## 1. Summary

Dye Essence is one machine with several sound engines behind one parameter table. Its first engine is a wavetable oscillator whose unison voices are SIMD lanes of the oscillator, not voices of their own; the next are virtual analog (Neo Poly's oscillators), sample and multisample, granular, harmonic (additive), modal and, last, spectral resynthesis. Each note has two filters (serial, parallel and anything between), amp and modulation envelopes with curves, LFOs drawn as breakpoints, and a modulation engine whose routes live in the machine's state while their amounts are parameters. An effects rack links the existing Neo engines (Drive, Ensemble, Delay, Verb, Comp, Multiband, EQ, Filter, Utility) as source.

Two layouts are templates of the same machine, not two machines:

| Layout | Sources | Modulators | Effects |
|---|---|---|---|
| **Trio** | 3 engine slots, a sub and a noise | 4 envelopes, up to 10 LFOs, 8 macros | 2 buses and a main chain |
| **Duo** | 2 engine slots and the utility block (sub, 2 noises, audio input later) | 3 envelopes, 3 LFOs, 3 functions, 3 randoms, 3 combinators, 4 macros | 2 inserts and an aux |

It is built in gated phases (§6). P0 is the gate: whether the renderer and ReBuzz can carry a synth of this size at all.

**Quality first.** "Really high quality" means measured, as for every Neo machine (machines.md §5): stated targets for aliasing per quality mode, bandwidth, pitch, envelope times, zipper, CPU, block-size independence, allocation and the null test, and presets levelled by the preset tools.

## 2. Decisions

| Decision | Choice | Why |
|---|---|---|
| Name | **Dye Essence**, the user's name; a Neo-family machine (built on the Neo kit, under machines.md's rules) without the "Neo" prefix | The user named it. Checks that find Neo machines by name or folder (`Neo*`) list it explicitly (the machine tests' project and the portable-maths scan already do) |
| One machine, two layouts | One parameter table, one manifest, one test suite, one preset format; Trio and Duo are templates (factory presets and editor pages) | Two machines from one source would double the manifests, presets, successor pairs and guides (analysis §5.2) |
| Layout names | Trio and Duo | Neutral and descriptive (three sources; two engines and the utility block). Never another product's name |
| Unison | Lanes of an oscillator (1–16), SIMD across lanes; a note voice owns its oscillators' lanes and has one pair of filters | Unison as voices (Neo Wave, Neo Poly) costs a full voice per unison voice; the gate measures the lane design (§5) |
| Filters | Run across notes: the 16 notes of a patch are lanes of one filter model | Every note of a patch has the same model; only cutoff and resonance differ |
| Parameter model | A + C (analysis §5.3): a union of each engine's parameters per slot, the slot's type picking which apply; topology in state (routes, FX order, drawn shapes, tables, samples); B (generic per-type parameters) only inside FX slots | Real units in the manifest, automatable, works with today's generator |
| Determinism | Machines.md §4 throughout: portable maths, element-wise SIMD, fixed-order sums, no FMA; three lane implementations held to the same bits by the tests | The null test across Windows, Linux and macOS |
| Successor | Of Neo Wave and Neo Poly (`machine_replace` pairs), once it covers them | No third overlapping synth (analysis §7.3) |
| Clip sequencer | Not built | The host has patterns, a piano roll and Session View |
| Content | Generated by code (tables as recipes), presets in units | No binary assets; nothing taken from another product |

## 3. Architecture

```
Machine "Dye Essence"
  Note input (tracks + MIDI; channel-aware for MPE in P4) → Arp/Seq (P4) → note allocator (poly ≤ 16 held, mono/legato, glide)
  NoteBank, structure of arrays, preallocated:
    per note × slot: IEngine { Wavetable | Analog | Sample | Multisample | Granular | Harmonic | Modal | Spectral }
                     each renders its unison lanes (SIMD) into the note's accumulators, at the voice rate (1× / 2× / 4×)
    per note: utility (sub, noise), mixer (level, pan, routing to filter 1, filter 2, direct)
    across notes: filter 1, filter 2 (serial ↔ parallel crossfade), amp; notes are lanes
    per note modulators: envelopes, LFOs/functions, randoms; global: macros, global LFOs, combinators, MIDI/MPE
  ModEngine: routes (source, destination, amount, aux, curve, rate) in state, amounts as parameters; per control tick, audio rate only where flagged
  Decimator (IIR halfband) → FX rack: Trio (bus A, bus B, main) | Duo (insert 1, insert 2, aux), Neo engines linked as source
  One stereo output
```

Files: `Machines/DyeEssence/` (the machine, its editor, `Params.def`, `Presets.txt`), `Machines/DyeEssence/Engine/` (pure DSP, tested in `NeoBuzz.MachineTests`), the studio flavour beside the other Neo machines'. Namespace `NeoBuzz.DyeEssence`.

## 4. The G0 renderer (as built in P0)

`Machines/DyeEssence/Engine/`: the core P1 builds on.

### 4.1 Lanes and the unison kernel

- **Lanes** (`Lanes.cs`). Eight float lanes and eight 32-bit integer lanes, behind one interface implemented three ways: one `Vector256` (x64 with AVX2), two `Vector128` halves (arm64, and x64 without AVX2) and eight plain floats (the reference). The kernels are generic over the implementation (C# static abstract members on structs), so the JIT compiles one specialised copy per implementation with every call inlined, and the operations are the same, in the same order, by construction. Sums across lanes run in one fixed order, ((0+4) + (1+5)) + ((2+6) + (3+7)). Comparisons and selects are bitwise; no min/max, no FMA, no estimates.
- **Tables** (`TableArena.cs`). A `NeoBuzz.Dsp.Wavetable` (frames of 2048, 11 band-limited mip levels by FFT, harmonics up to 1024 >> level) in one array; every level a power of two long, each with Wavetable's three guard samples. A 256-frame table takes 19.7 MB.
- **The kernel** (`UnisonKernel.cs`). Per oscillator of a note and per control tick: one mip level (for the highest lane's pitch) and one frame pair, shared by every lane. Per lane: a 32-bit phase (exact, the wrap free; frequency resolution 2.2·10⁻⁵ Hz at 96 kHz), the read index and its fraction by shifts, the four points of each frame as one 16-byte load per lane and a 4×4 transpose (data movement only: exact, faster than four gathers on x64, and arm64 has no gather), the frame morph, then the 4-point cubic in Wavetable's order of operations; each lane's gain and pan ramped across the tick into the note's accumulators.
- **Unison**: 1–16 lanes per oscillator, in groups of eight (a stack of 1–8 costs one group). The lanes' pitches spread evenly over `Detune` semitones, their pans over `Spread`, each lane at 1/√U; seeded random start phases (one lane: phase 0).
- **Rates**: voices at 1× or 2× the sample rate; at 2× an IIR halfband (Neo Wave's) decimates, and mip levels keep harmonics under 44 kHz; at 1× under Nyquist.

### 4.2 Notes, filters, the control grid

- **NoteBank** (`NoteBank.cs`): 16 note slots × 3 oscillators × 16 lanes, every array allocated at construction.
- **Filters across notes** (`NoteFilters.cs`): NeoBuzz.Dsp's ladder (LP24/LP12, the tanh at its input) and state-variable filter (Simper's, every mode), the same operations per lane, coefficients per note per tick; stereo, both channels in one loop. Filter 2 hears filter 1 (serial, 0), the oscillators (parallel, 1) or a crossfade; the output is f2 + routing · f1.
- **Control grid**: every 16 base-rate samples on a grid that runs across blocks; control values (pitches, levels, frames, coefficients, the envelopes' levels) change only on it and ramp across the whole tick, and a note started mid-tick gets its values for the rest of it, so blocks of any size give the same samples.
- **Envelopes** (G0): NeoBuzz.Dsp's ADSR stepped at the voice rate per tick, the amp's gain ramped linearly across the tick. P1 replaces them with envelopes with curves (§6).

### 5.1 Renderer

### 5.2 ReBuzz with ~700 parameters and large state

**Dye Stress** (`ReBuzz.Studio.Tests/TestMachines/DyeStress/`, not shipped): 704 parameters shaped as Dye Essence's table will be (option A: three slots of 99, utility, two filters, amp, four envelopes, ten LFOs, functions, randoms and combinators, eight macros, 64 route amounts, ten FX slots of ten, arpeggiator, MPE and tuning), its `Params.def` written by `make-params.py` and its code and manifest by `tools/gen-machine-params.py`; 16 tracks of Note and Velocity; a machine state of 8.4 MB (three 256-frame tables as base64 floats, as Neo Wave keeps a user table, and 64 routes as text). Measured in the studio, headless (`DyeStressTests`), on both runners:

Runs 42212607166 (Linux x64) and 42212610289 (macOS arm64), on 7f266231:

**Found and fixed in P0** (outside Dye Essence; each covered by the stress test):
- **The studio's pattern editor drew every column of a set on every frame.** A machine's globals are one column set, so a frame laid out the text of all 704 columns: locally (a busy two-core machine) 1.25 s a frame against Neo Poly's 41 ms, 2.1 s to open. `PatternGrid.DrawBeat` and the column labels now take only the columns in view (`ModernPatternEditor/Avalonia/PatternGrid.cs`): locally 69–88 ms, on the runners 3–16 ms.
- **`.bmx` lost MIDI bindings past the 256th state parameter.** Buzz's MIDI section stores the parameter index in a byte, so a binding of parameter 512 came back on parameter 0 (Neo Sampler, with 325 parameters, was already affected). A new `MID2` section holds every binding with a 16-bit track and index and is read instead when a file has it; Buzz's section keeps the bindings that fit, so Buzz and earlier versions read those as before (`ReBuzz/FileOps/BMXFile.cs`).

**Found, not fixed** (for the lead to schedule):
- **`machine_describe` without a group returns every parameter**: 326 KB of JSON at 704, far more than an agent should read at once. For agents, P1c makes a large machine's describe answer with its groups (names, counts) unless a group is asked for (one group is 45 KB), and the guide works page by page.
- **The studio's parameter window builds every row up front** (a `StackPanel` of `ParameterRow`s): 0.3–0.4 s at 704 on the runners, seconds on a busy machine. Acceptable for the fallback view (Dye Essence's own editor is its main face); virtualising the rows would remove it.
- **Not measured**: the WPF parameter window and the WPF pattern editor in NeoBuzz Live on Windows (they need the app's main window and theme files, which ReBuzzTests doesn't have). The WPF pattern editor caches a drawn beat per column set and culls only vertically, so its cost would show when a beat is redrawn (an edit), not on every frame.

### 5.3 Recommendation: go, with these adjustments

- **Go.** The renderer runs the gate's case at 11× real time on x64 and 10× on arm64 (target 2×), the same bits on both, and ReBuzz carries 704 parameters and 8 MB of state through songs, presets, patterns, MIDI learn and the agent, with the two fixes above.
- **Unison budget: 16 per oscillator**, as the targets have: 16 notes × 3 × 16 runs at 7× and 6×.
- **Quality modes**: **Standard 2×** (the default; the measured figures), **High 4×** for audio-rate FM/PM and the sync-type warps (P1a measures their alias floors at 2× and 4× and sets the mode per warp), and no 1× mode for users: at 1× the top octave of harmonics goes (nothing above 14 kHz at 440 Hz), which is not this machine's quality, and 2× is affordable.
- **P1a optimisations, measured as they land**: lane sums across eight samples at once (a transpose instead of a horizontal sum per sample); envelopes in closed form per tick; unison stacks of 1–4 lanes in a 4-lane group, or lanes of several oscillators packed into one group.
- **Before Dye Essence ships (P1c)**: the large-machine `machine_describe` (agent server); the WPF parameter window and pattern editor checked by hand in NeoBuzz Live with Dye Essence; optionally the studio's parameter window virtualised.

## 7. Parameters, state and presets

- **Append-only once shipped**: the table's order, ranges and saved meaning never change after a phase merges; new parameters go at the end; enums have room to grow (an enum's maximum can grow; its values never move). So P1a ships slots with room for every engine type to come.
- **Budget** (analysis §5.3): slots 3 × ≈90, utility ≈15, filters 2 × ≈11, amp ≈6, envelopes 4 × 8, LFOs 10 × ≈8, functions, randoms and combinators ≈45, macros 8, route amounts 64, FX ≈140, arp ≈15, voice and global ≈15: ≈700.
- **State** (`MachineState`, XML): routes, FX order, drawn shapes, user tables (raw 2048-sample frames; mip levels rebuilt on load), sequences. Built-in tables are recipes, never data.
- **Presets**: ReBuzz's own presets already carry a machine's data (`Preset(machine, false, includedata: true)`, the editor kit's Save), so a user preset keeps its tables and routes. Factory presets are written in units in `Presets.txt` with their state as text (recipes, routes) once the preset generator learns a `state` line (P1).

## 8. Editor (P1c)

Pages (Play, Oscillators, Filters, Modulation, Effects, Arp later), drawn on the kit's `INeoCanvas` so WPF and Avalonia share one source; drag-from-source modulation with rings on the knobs; breakpoint drawing; a route list; the rack list; the 3-D table view from Neo Wave. Gestures are one undo step each; state edits (routes, shapes, tables) get undo entries of their own.

## 9. Agents (P1c)

Every parameter in real units in the generated manifest; routes through a new tool or a `machine_data` kind; tables per slot through `ImportData`; a guide grouped by page. Sound matching by render and compare, never by importing another product's presets.

## 10. IP (clean-room)

- No other product's name in machine, template, preset or UI text or in user docs; describing file compatibility ("reads WAV wavetables with a `clm` chunk") is fine.
- No copied code, tables, presets, layouts or artwork; no GPL code in these MIT machines. Methods from the published literature (BLEP, ADAA, ZDF, FDN, granular, additive, modal, phase vocoder) and our own measurements.
- The look is the Neo theme.

## 11. Picking the work up

- Worktree per phase from `origin/main` (the agent conventions); build only the portable projects on Linux with the offline NuGet config; WPF and ReBuzzTests run on the package run.
- `dotnet test NeoBuzz.MachineTests --filter FullyQualifiedName~DyeEssence` runs the engine's tests; `Measure.Report` lines are the figures (CI shows them in its notices and logs).
- The pinned checksum (`DyeEssenceTests.PinnedGateHash`) changes whenever the renderer's arithmetic does: re-pin it from the Linux run and confirm the Mac run matches before merging.
